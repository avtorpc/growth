# Growth — импорт заказов цветочного магазина

Монолит Symfony, Angular и MySQL 8. Вся Docker-инфраструктура находится в `docker/`.

## Требования

- Установленный и запущенный Docker Desktop либо Docker Engine с Docker Compose v2,
  поддерживающим `--wait`.
- Интернет при первой сборке для загрузки образов и зависимостей.
- Свободные локальные порты `8080` для приложения и `3307` для MySQL.

PHP, Composer, Node.js и MySQL устанавливаются внутри контейнеров. Локально они не нужны.

## Первый запуск

Открой терминал и перейди в корень репозитория. На текущем компьютере:

```sh
cd /Users/user/Documents/_test_Growth
```

На другой машине используй путь к своей копии репозитория. Все дальнейшие команды
выполняются из его корня.

### 1. Собрать и запустить окружение

```sh
docker compose -f docker/compose.yaml up -d --build --wait
```

Команда собирает образы бэкенда и фронтенда, устанавливает зависимости и запускает
четыре сервиса: `nginx`, `backend`, `frontend`, `database`. Флаг `-d` оставляет их
работать в фоне, `--wait` ждёт готовности сервисов. Первый запуск может занять несколько минут.

**Файл `.env` для запуска не требуется.** Все необходимые значения по умолчанию
заданы в `docker/compose.yaml`.

### 2. Применить миграции базы

```sh
docker compose -f docker/compose.yaml exec backend php bin/console doctrine:migrations:migrate --no-interaction
```

Миграции создают таблицы, тестовый магазин с ID `1` и четыре тарифа доставки.
Повторный запуск пропускает уже выполненные миграции. После появления новых миграций
эту команду нужно выполнить снова.

### 3. Открыть и проверить приложение

Открой [http://localhost:8080](http://localhost:8080).
На странице нажмите «Загрузить заказы». Angular загрузит тестовый JSON из ассетов,
отправит его в API магазина № 1 и покажет результат каждой записи: создан, обновлён,
без изменений, дубль или отказ с причиной. Доступен фильтр по результату обработки.
Для сохранённых заказов показаны статус, сумма позиций, доставка и итог; несовпадение
суммы маркетплейса выделяется отметкой «Нужна проверка суммы».

В текущей локальной базе набор уже импортирован: повторная загрузка показывает
7 записей без изменений, 3 отказа и 1 дубль. Новые копии заказов не создаются.
При ошибке запроса выводится сообщение и можно повторить загрузку.
Постоянный список сохранённых заказов с пагинацией — отдельный следующий этап.

Проверка API, если на компьютере доступен `curl`:

```sh
curl -fsS http://localhost:8080/api/health
```

Ожидаемый ответ:

```json
{"status":"ok","database":"ok"}
```

Поле `orders.outcome` хранит результат последней успешной обработки сохранённого
заказа (`created`, `updated`, `unchanged`). Оно отдельно от статуса заказа и
не является историей импортов. Подробнее — в [IMPORT.md](IMPORT.md).

## Импорт заказов через API

Из корня проекта:

```sh
curl -fsS -X POST http://localhost:8080/api/shops/1/orders/import \
  -H 'Content-Type: application/json' \
  --data-binary @frontend/src/assets/marketplace-orders.json
```

Первый импорт в пустой магазин создаёт 7 заказов, отклоняет 3 записи и отмечает 1 дубль.
Повтор той же пачки возвращает 7 записей без изменений, те же 3 отказа и 1 дубль.
В ответе есть результат и причина для каждой записи. Контракт: [IMPORT.md](IMPORT.md).

## Подключение к MySQL с компьютера

В клиенте базы данных выбери тип подключения MySQL:

| Параметр | Значение по умолчанию |
|---|---|
| Хост | `127.0.0.1` |
| Порт | `3307` |
| База | `growth` |
| Пользователь | `growth` |
| Пароль | `growth_local_password` |
| SSH-туннель | Не требуется |
| SSL | Для локального окружения не требуется |

Внутри Docker бэкенд использует адрес `database:3306`. База опубликована только
на локальном интерфейсе. Доступы предназначены для разработки.

Данные сохраняются в Docker-томе `growth_mysql_data`. Обычная остановка проекта
их сохраняет. Команда `down -v` удаляет том и данные, поэтому для обычной остановки
используй `down` без `-v`.

## Повседневные команды

```sh
# Состояние контейнеров
docker compose -f docker/compose.yaml ps

# Последние сообщения всех сервисов
docker compose -f docker/compose.yaml logs --tail=100

# Следить за сообщениями бэкенда (выход из просмотра — Ctrl+C)
docker compose -f docker/compose.yaml logs -f backend

# Остановить окружение, сохранив базу
docker compose -f docker/compose.yaml down

# Запустить уже собранное окружение
docker compose -f docker/compose.yaml up -d --wait

# Пересобрать после изменения зависимостей или Docker-конфигурации
docker compose -f docker/compose.yaml up -d --build --wait

# Проверить правила, схему базы и импорт
docker compose -f docker/compose.yaml exec backend vendor/bin/phpunit

# Проверить конфигурацию Symfony
docker compose -f docker/compose.yaml exec backend php bin/console lint:container

# Проверить сборку Angular
docker compose -f docker/compose.yaml exec frontend npm run build
```

Изменения в `backend/src` и `frontend/src` доступны в работающих контейнерах без
пересборки. После изменения зависимостей повтори сборку; после добавления миграций
примени их отдельной командой.

Если запуск завершился ошибкой, проверь состояние контейнеров и последние сообщения
командами `ps` и `logs` выше. При ошибке занятого порта измени настройки, как описано ниже.

## Необязательные настройки через .env

Чтобы изменить порт или другие значения, создай локальный файл настроек:

```sh
cp docker/.env.example docker/.env
```

Выполняй копирование только при отсутствии `docker/.env`, чтобы сохранить свои настройки.
Измени нужные значения в этом файле: `APP_PORT` — порт приложения,
`MYSQL_PORT` — локальный порт MySQL. Затем запусти окружение с явным указанием файла:

```sh
docker compose --env-file docker/.env -f docker/compose.yaml up -d --build --wait
docker compose --env-file docker/.env -f docker/compose.yaml exec backend php bin/console doctrine:migrations:migrate --no-interaction
```

При использовании своих настроек добавляй `--env-file docker/.env` и к остальным
командам Compose. Адреса и доступы в разделах выше соответствуют значениям по умолчанию.
Изменение паролей в файле не меняет учётные записи в уже созданном томе MySQL.
Файл `docker/.env` исключён из Git; шаблон `docker/.env.example` хранится в репозитории.

## Структура проекта и документация

- `backend/` — монолит Symfony; `backend/migrations/` — миграции базы.
- `frontend/` — приложение Angular.
- [marketplace-orders.json](frontend/src/assets/marketplace-orders.json) — валидная фикстура
  из 11 записей; доступна по `/assets/marketplace-orders.json`. Исправлены переносы строк,
  намеренные ошибки данных сохранены.
- `docker/` — Docker Compose, Dockerfile и конфигурация Nginx.
- [IMPORT.md](IMPORT.md) — API импорта, причины отказов и ограничения свежести данных.
- [DATABASE.md](DATABASE.md) — таблицы, связи, начальные данные и доступы к базе.
- [DECISIONS.md](DECISIONS.md) — журнал решений, ограничения, проверки и время работы.

# Исходное тестовое задание

Контекст
Мы делаем SaaS для цветочных магазинов: бэкенд на PHP/Symfony, фронтенд на Angular,
база MySQL. Задача — упрощённая версия того, что мы делаем постоянно: приём заказов
из внешней площадки, расчёт доставки и неидеальные входные данные. Все данные
вымышленные.
Мы оцениваем решения, а не объём. Задача намеренно шире, чем стоит делать в
тестовом. Что сделать тщательно, что упростить, а что оставить — часть задания. Так же
выглядит обычная работа в Growth-команде: задач всегда больше, чем времени.
Лимита времени нет, и больше часов не значит выше оценка. Нам важно другое: чтобы вы
записали, сколько потратили и на что, и могли объяснить, почему потратили именно так.
AI-инструменты (Claude Code, Cursor и другие) использовать можно и нужно, как в
обычной работе. Условие одно: вы понимаете каждую строку и объясните её на встрече.
Задача
Нужен мини-модуль: магазин нажимает «Загрузить заказы», система принимает пачку
заказов маркетплейса, сохраняет их, считает доставку и показывает результат.
Что должен смочь магазин:
загрузить заказы и понять, что случилось с каждым: создан, обновлён, без изменений,
дубль или отклонён — и почему;
увидеть список своих заказов со стоимостью доставки и итогом, отфильтровать его по
статусу;
делать это с телефона — большинство наших пользователей работают с него;
не получить дублей, даже если нажал кнопку дважды или два импорта пришли
одновременно.
Маркетплейс заменяет фикстура marketplace-orders.json (приложена к заданию, текст — в
конце документа). Реальная интеграция не нужна.
Что неизменно
Это единственные твёрдые условия. Всё остальное решаете вы.
Стек. PHP 8.2+, Symfony, MySQL 8, Angular. Мы пишем на современном Angular
(standalone-компоненты, signals) — это контекст, а не требование. UI-библиотеки
разрешены, дизайн не оцениваем.
Запуск. Мы должны поднять проект на чистой машине по вашей инструкции через Docker.
Если не запустилось — мы не сможем оценить остальное.

Стр. 1 из 4

Правила импорта. Это бизнес-логика магазина, она не обсуждается:
1. Заказ определяется парой «магазин + id маркетплейса». Повторный или
одновременный импорт того же файла не создаёт дублей.
2. Один плохой заказ не роняет пачку: он отклоняется с причиной, остальные
сохраняются.
3. Обязательны: идентификатор, статус, имя и телефон покупателя, хотя бы одна позиция;
для доставки ещё район, адрес и интервал. Телефон приводится к +7XXXXXXXXXX
(принимаем 8... , пробелы, дефисы, скобки), иначе заказ отклоняется.
4. Статусы: NEW → new, ACCEPTED → accepted, IN_DELIVERY → delivering, DONE → delivered,
CANCELED → cancelled. Неизвестный статус — отказ.
5. При повторном импорте меняется только статус. Финальные статусы delivered и
cancelled назад не откатываются. Повтор того же id в одной пачке — дубль, первое
вхождение обрабатывается обычно.
6. Если сумма позиций (qty × price) не совпадает с total , заказ сохраняется с пометкой
«нужна проверка». Для расчётов берём сумму позиций.
Доставка. Самовывоз стоит 0. Доставка = базовая цена района (бесплатно от порога
суммы позиций) + 200 ₽ за срочность, если начало интервала меньше чем через 2 часа
после created_at . Бесплатная доставка обнуляет только базовую цену. Район без тарифа —
отказ с кодом unknown_district .
Что решаете вы
Ниже — развилки, на которых мы намеренно не даём ответа. Нам интересно, что вы
выберете и как объясните. «Не делал, потому что...» — нормальный ответ.
Тесты. Писать или нет, на что именно, на каком уровне (юнит, интеграционные, e2e).
Что в этой задаче сломается первым и незаметнее всего?
Идемпотентность. Чем именно гарантировано отсутствие дублей при одновременных
запросах и что увидит второй запрос.
Данные. Как хранить позиции заказа, деньги, время и часовые пояса; какие индексы
нужны.
API. Форма эндпоинтов, формат ответа импорта, коды ошибок, пагинация.
Расчёт доставки. Где живут тарифы и насколько легко добавить новое правило. Когда
считать: при импорте или при чтении.
Фронтенд. Какие состояния интерфейса важны, как показать отказы по каждому
заказу, как сделать таблицу удобной на телефоне.

Неоднозначности в данных. В фикстуре есть места, где правила можно прочитать по-
разному. Выберите трактовку и запишите её.

Порядок работы. С чего начать, где остановиться, что оставить на потом.
AI. Для чего использовать и что проверять за ним.
Что точно не нужно: авторизация, деплой, CI, очереди, многоязычность, красивый дизайн.
Если добавите — спросим, чем ради этого жертвовали.
