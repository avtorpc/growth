# Тестовая база данных

## Подключение с компьютера

В DBeaver, DataGrip, TablePlus или другом клиенте создать подключение MySQL:

| Параметр | Значение |
|---|---|
| Хост | `127.0.0.1` |
| Порт | `3307` |
| База / схема | `growth` |
| Пользователь | `growth` |
| Пароль | `growth_local_password` |
| SSH-туннель | Не требуется |
| SSL | Для этого локального окружения не требуется |

Доступ проверен с локального компьютера. MySQL опубликована только на loopback-адресе.
Параметры по умолчанию заданы в `docker/.env.example` и `docker/compose.yaml`.
Переопределения можно задать в `docker/.env`; локальный порт — `MYSQL_PORT`.
Внутри Docker бэкенд подключается к `database:3306`, используя ту же базу и пользователя.

Если установлен клиент MySQL:

```sh
mysql --protocol=TCP -h 127.0.0.1 -P 3307 -u growth -p growth
```

Пароль вводится по запросу клиента. Без локального клиента:

```sh
docker compose -f docker/compose.yaml exec database mysql --default-character-set=utf8mb4 -u growth -p growth
```

## Где находится база и как создать таблицы

MySQL 8.0 работает в сервисе `database` (`growth-database-1`). Данные находятся в
Docker-томе `growth_mysql_data`, подключённом к `/var/lib/mysql` внутри контейнера.
На macOS том хранится в виртуальной машине Docker Desktop.

Из корня проекта:

```sh
# Если docker/.env ещё не создан, можно скопировать docker/.env.example
docker compose -f docker/compose.yaml up -d --build --wait
docker compose -f docker/compose.yaml exec backend php bin/console doctrine:migrations:migrate --no-interaction
```

Таблицы создаются миграциями приложения из `backend/migrations/`, а не Docker-скриптами.
Первая миграция создаёт структуру, вторая — тестовый магазин и тарифы. Doctrine хранит
выполненные версии: повторный запуск не создаёт дубли. После обновления кода с новыми
миграциями нужно повторить вторую команду. Миграции запускаются отдельно от старта API.

## Созданные таблицы

Все таблицы находятся в базе `growth`, используют InnoDB и внешние ключи.

| Таблица | Назначение и основные поля |
|---|---|
| `shops` | Магазины: `id`, уникальный `code`, `name`, `timezone`, `urgent_surcharge_kopecks`, `created_at` |
| `delivery_tariffs` | Тарифы магазина: `shop_id`, `district_code`, `base_price_kopecks`, `free_from_kopecks` |
| `orders` | Заказы: `shop_id`, `marketplace_id`, `status`, данные покупателя, время создания на площадке, способ и данные доставки, денежные суммы, отметка проверки, время импорта и обновления |
| `order_items` | Позиции: `order_id`, порядковый `position`, `sku`, `name`, `quantity`, `unit_price_kopecks`, сумма строки |
| `doctrine_migration_versions` | Служебная таблица истории миграций |

Связи: `shops → delivery_tariffs`, `shops → orders`, `orders → order_items`.
При удалении заказа удаляются его позиции. Удаление магазина, на который ссылаются
заказы или тарифы, блокируется внешними ключами.

### Заказы и денежные поля

- `items_total_kopecks` — сумма позиций, рассчитанная приложением при импорте.
- `marketplace_total_kopecks` — исходный `total` площадки, переведённый в копейки.
- `needs_review` — вычисляемая отметка несовпадения этих сумм.
- `delivery_base_kopecks` — применённая базовая цена с учётом бесплатного порога.
- `delivery_surcharge_kopecks` — применённая надбавка за срочность.
- `delivery_total_kopecks` — вычисляемая сумма двух составляющих доставки.
- `grand_total_kopecks` — вычисляемый итог: сумма позиций плюс доставка.
- `order_items.line_total_kopecks` — вычисляемое произведение количества и цены.

Деньги хранятся целыми числами `BIGINT` в копейках. Цены и суммы неотрицательны,
количество позиций — положительное целое. Вычисляемые поля отдельно не записываются.
Тарифы в заказе сохраняются как снимок расчёта; изменение справочника не меняет
стоимость уже импортированных заказов.

`marketplace_created_at`, `delivery_from`, `delivery_to`, `imported_at`, `updated_at`
используют `DATETIME(6)` и UTC. Сессия MySQL также работает в UTC. Поле `timezone`
заказа сохраняет зону магазина на момент импорта; тестовый магазин — `Europe/Moscow`.
Приложение должно переводить московскую дату и интервал доставки в UTC до записи.

### Ограничения и индексы

- Уникальная пара `orders(shop_id, marketplace_id)` защищает от создания дублей
  на уровне базы, в том числе при параллельной вставке. Обработка результата второго
  запроса появится вместе с импортом.
- ID площадки чувствителен к регистру, максимум 128 символов. Пустой ID запрещён.
- Индексы `orders(shop_id, id)` и `orders(shop_id, status, id)` предназначены для
  списка магазина, фильтра по статусу и пагинации по ID.
- Пара `delivery_tariffs(shop_id, district_code)` уникальна.
- Пара `order_items(order_id, position)` уникальна; одинаковый SKU в разных строках допустим.
- Статусы ограничены `new`, `accepted`, `delivering`, `delivered`, `cancelled`.
- Телефон хранится только в формате `+7XXXXXXXXXX`.
- Для доставки обязательны район, адрес и возрастающий интервал. Для самовывоза
  поля адреса и интервала пусты, стоимость доставки равна нулю.

Наличие хотя бы одной позиции, сумму позиций для `items_total_kopecks`, поиск тарифа,
расчёт срочности и защиту финальных статусов проверяет сервис импорта.
Заказ и позиции записываются одной транзакцией. Триггеры для этих правил не добавлены.

## Начальные данные

Магазин: `id = 1`, `code = demo`, имя «Тестовый цветочный магазин»,
часовой пояс `Europe/Moscow`. Надбавка за срочность — 200 ₽ (`20000` копеек).

| Район | Базовая цена, ₽ | Бесплатно от суммы позиций, ₽ |
|---|---:|---:|
| `centre` | 300 | 5000 |
| `north` | 400 | 7000 |
| `south` | 400 | 7000 |
| `suburb` | 700 | Нет (`NULL`) |

12 октября 2026 фикстура загружена через API: в магазине `1` сохранены 7 заказов
и 7 строк позиций. Три записи отклонены, второе вхождение MP-1001 отмечено дублем.
Повторный импорт не создал дополнительных строк. MP-1009 имеет отметку `needs_review`.
Отказы и дубли возвращаются в ответе API; отдельного постоянного журнала импортов нет.

## Проверка

```sh
docker compose -f docker/compose.yaml exec backend vendor/bin/phpunit
docker compose -f docker/compose.yaml exec backend php bin/console doctrine:migrations:status
```

Проверки схемы выполняют вставки внутри транзакций с откатом. Проверки импорта
используют отдельные тестовые магазины и удаляют свои записи после выполнения,
не изменяя магазин `1`. Проверены ограничения данных, уникальность в пределах
магазина, внешние ключи, денежные итоги, исходные тарифы, UTC и конкурентный импорт.
