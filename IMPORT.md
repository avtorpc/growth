# Импорт заказов

## Запрос

После запуска окружения и применения миграций, из корня репозитория:

```sh
curl -fsS -X POST http://localhost:8080/api/shops/1/orders/import \
  -H 'Content-Type: application/json' \
  --data-binary @frontend/src/assets/marketplace-orders.json
```

API принимает объект `{"orders": [...]}`. Магазин задаётся в адресе, ID заказа на
маркетплейсе — поле `id` каждой записи. Максимум 1000 записей и 1000000 байт на запрос.
Пустая пачка допустима и возвращает нулевые счётчики.

## Ответ для фронтенда

HTTP 200 означает, что пачка обработана; результат каждой записи находится в `results`.
Отказы отдельных заказов не превращают всю пачку в ошибку HTTP.

```json
{
  "shop_id": 1,
  "total": 11,
  "summary": {
    "created": 7,
    "updated": 0,
    "unchanged": 0,
    "duplicate": 1,
    "rejected": 3
  },
  "results": [
    {
      "index": 6,
      "marketplace_id": "MP-1006",
      "outcome": "rejected",
      "reason": {
        "code": "unknown_district",
        "message": "Для района zarechye нет тарифа доставки."
      },
      "warnings": []
    }
  ]
}
```

Полный пример фактического первого ответа сохранён в
[docs/examples/import-response.json](docs/examples/import-response.json). Внутренние
ID в примере назначены текущей базой и могут отличаться при новом запуске.

Выше показана одна из 11 строк `results` для краткости. `index` начинается с 1
и соответствует позиции во входной пачке. Если ID невозможно прочитать, он равен
`null`, но строка всё равно имеет индекс и причину отказа.

| `outcome` | Значение |
|---|---|
| `created` | Заказ и позиции созданы |
| `updated` | Обновлён только статус существующего заказа |
| `unchanged` | Статус тот же либо сохранён финальный статус |
| `duplicate` | ID уже встречался в этой пачке |
| `rejected` | Заказ не прошёл проверку или его не удалось сохранить |

Все строки имеют `reason.code`, `reason.message` и массив `warnings`. Для сохранённых
заказов есть объект `order`: внутренний `id`, сохранённый `status`, `needs_review`,
`items_total_kopecks`, `marketplace_total_kopecks`, `delivery_total_kopecks`,
`grand_total_kopecks`. Суммы выражены в копейках; ответ повторного импорта показывает
именно сохранённые суммы, даже если входные позиции отличаются.

Несовпадение суммы позиций с `total` даёт предупреждение `total_mismatch` и
`needs_review: true`. Это не отказ. `final_status_preserved` объясняет, почему новый
статус не применён к завершённому или отменённому заказу.

Основные коды отказа: `unknown_district`, `invalid_phone`, `unknown_status`,
`invalid_field`, `invalid_items`, `invalid_quantity`, `invalid_money`,
`invalid_created_at`, `invalid_delivery_type`, `invalid_district`,
`invalid_interval`, `delivery_before_creation`, `storage_error`.

Ошибки всего запроса имеют форму `{"error":{"code":"...","message":"..."}}`:

| HTTP | Ситуация |
|---|---|
| 400 | Невалидный JSON, неверная форма пачки или больше 1000 записей |
| 404 | Магазин не существует |
| 413 | Превышен размер запроса |
| 415 | Не указан `Content-Type: application/json` |
| 503 | База недоступна при получении магазина и тарифов |

`storage_error` откатывает текущий заказ; обработка следующих записей продолжается.
Повторить всю пачку безопасно: успешно сохранённые заказы не дублируются.

## Правила

- Обработка идёт в исходном порядке. ID запоминается до полной проверки данных:
  повтор первого отклонённого заказа в той же пачке тоже считается дублем.
- Каждый входной заказ проходит полную проверку, даже если уже существует.
  Повторный импорт не изменяет покупателя, дату создания, позиции и стоимость доставки.
- Для существующих нефинальных заказов разрешено изменение статуса в любом направлении;
  задание не задаёт дополнительных ограничений переходов. `delivered` и `cancelled`
  остаются финальными, в том числе не переходят друг в друга.
- `created_at` требует ISO-дату со временем до секунд и явным часовым поясом.
  Доставка трактуется в зоне магазина; в базу все моменты записываются в UTC.
- Начало доставки не может быть раньше создания заказа, конец должен быть позже начала.
  Исторические даты допустимы. При задержке от 0 до 7199 секунд действует надбавка;
  ровно 7200 секунд — без надбавки. Ночные интервалы через полночь пока не поддерживаются.
- Самовывоз не требует адреса и тарифа; дополнительные поля доставки для него игнорируются.
- Бесплатный порог включителен и применяется к сумме позиций. Надбавка сохраняется.
- Деньги принимаются в рублях как числа или десятичные строки, неотрицательные,
  максимум два десятичных знака. Экспоненциальные строки не принимаются. Лимит суммы,
  включая доставку, — 1000000000000 копеек; количество — целое от 1 до 1000000.
- Каждая позиция требует имени, количества и цены; SKU необязателен. Максимум 1000
  позиций на заказ. `total` и `created_at` обязательны. Пробелы по краям текстовых полей
  обрезаются; телефон нормализуется из +7, 7 или 8 с пробелами, скобками и дефисами.

## Конкурентный импорт

`UNIQUE(shop_id, marketplace_id)` защищает вставку. Заказ и позиции сохраняются
одной транзакцией; существующая строка блокируется через `SELECT ... FOR UPDATE`
перед проверкой финального статуса. При конфликте вставки или взаимной блокировке
транзакция откатывается и повторяется до трёх попыток с короткой задержкой.

В двух одновременно обработанных одинаковых пачках результат `created` может быть
распределён между запросами. В сумме они создают семь заказов; остальные валидные
повторения получают `unchanged`. Внутрипакетный дубль остаётся в каждой пачке.

## Свежесть данных в реальной интеграции

`created_at` — время создания заказа, оно не показывает время изменения статуса.
События могут приходить с задержкой и в другом порядке, в том числе между пачками.
В текущей фикстуре нет данных, по которым можно определить свежесть обновления.
Поэтому применяется очередной полученный статус с защитой финальных состояний.

Для реального обмена нужны `updated_at` площадки или, предпочтительно, монотонная
версия заказа, сохранённая вместе с ним. При обновлении нужно атомарно сравнивать
версию и отбрасывать устаревшие события; для равных времён — определить дополнительный
порядок. Локальный `orders.updated_at` фиксирует время нашей записи и не заменяет
версию или время обновления на площадке.

## Проверки

```sh
docker compose -f docker/compose.yaml exec backend vendor/bin/phpunit
```

Тесты используют отдельные магазины, не изменяют заказы магазина `1` и удаляют свои
данные после выполнения. Параллельные проверки запускают два независимых PHP-процесса
с общим сигналом старта. Проверяются первое и повторное получение фикстуры, конкуренция,
только статус при обновлении, оба финальных статуса, изоляция отказов, откат заказа при
ошибке вставки позиции, денежные границы, время, телефоны и HTTP-контракт.

## Импорт через Angular

На http://localhost:8080 нажмите «Загрузить заказы». Клиент читает
`/assets/marketplace-orders.json`, затем передаёт полученный объект без изменения
в `POST /api/shops/1/orders/import`. Расчёт и проверка данных выполняются бэкендом.

Пока запрос выполняется, кнопка заблокирована. После ответа отображаются общие
счётчики и карточка каждой входной записи, включая отказы и дубли. Карточки
отслеживаются по номеру записи, поскольку один marketplace_id может встретиться
дважды. Фильтр позволяет оставить только нужный результат; счётчики относятся
ко всей пачке. Суммы из API переводятся из копеек в рубли только для отображения.

Перед новым запуском предыдущий отчёт очищается. Ошибка загрузки файла, ошибка
API и отсутствие ответа отображаются отдельно. При сетевой ошибке или таймауте
клиент предупреждает, что часть данных могла сохраниться и повтор безопасен.
Таймаут чтения файла — 10 секунд, запроса импорта — 30 секунд.
Отчёт хранится в памяти страницы до следующей загрузки или перезагрузки вкладки.

## Результат обработки в таблице orders

`orders.outcome` хранит результат последней успешной обработки сохранённого заказа:
`created`, `updated` или `unchanged`. Поле обновляется в той же транзакции, что и
заказ; оно не меняет бизнес-статус `orders.status`. При повторе без изменений
обновляется только `outcome`, дата изменения бизнес-данных `updated_at` сохраняется.

Для записей, созданных до миграции, значение `NULL` означает, что результат
прошлой обработки неизвестен. Следующий успешный импорт заполнит поле.
Дубль внутри пачки не перезаписывает результат первого вхождения. Отказ
не создаёт запись в `orders` и не меняет результат предыдущей успешной обработки
существующего заказа. Эти результаты по-прежнему возвращаются в отчёте API.

Это последнее значение, а не журнал: новый успешный импорт перезаписывает старое.
История попыток и отклонённые записи сохраняются отдельно в журнале, описанном ниже.

## Постоянный журнал и отказы

Миграция `Version20261012020000` создаёт три таблицы:

| Таблица | Содержимое |
|---|---|
| `order_imports` | Запуск: магазин, число входных записей, состояние, счётчики, время начала и окончания |
| `order_import_records` | Каждая входная запись: запуск, номер в пачке, прочитанный ID маркетплейса, ссылка на заказ при успешной обработке, outcome, исходный JSON и снимок ответа API |
| `rejected_orders` | Каждый отказ: ссылка на запись журнала, исходный JSON, код и текст причины, время отказа |

Ответ POST дополнен `import_id` — ID запуска. Остальные поля ответа сохраняются,
поэтому Angular продолжает показывать результаты как раньше. Состояния запуска
`processing`, `completed`, `failed` относятся к выполнению пачки, а не к статусам заказов.
`completed` означает обработку всех записей, даже если некоторые отклонены.

Каждая повторная загрузка создаёт новый запуск и новые записи журнала, в том числе
повторные отказы. Рабочие заказы по-прежнему не дублируются. После исправления данных
заказ создаётся обычным импортом; прежний отказ остаётся в истории. Дубли внутри
пачки записываются в журнал с outcome=duplicate, но не в rejected_orders.

Принятый заказ и его запись журнала сохраняются одной транзакцией. При ошибке
сохранения заказа выполняется откат и отдельная запись отказа storage_error.
Запись отказа и её запись журнала также атомарны. Если журнал недоступен, запрос
завершается ошибкой 503; уже завершённые транзакции сохраняются. Состояние запуска
по возможности становится failed; при потере соединения или завершении процесса
может остаться processing. summary содержит только результаты записанных строк.

В журнал попадают только пачки, прошедшие проверку формы HTTP-запроса для
существующего магазина. Невалидный JSON, неподдерживаемый тип, слишком большой
запрос и неизвестный магазин не создают запуск. Пустая корректная пачка создаёт
завершённый запуск без строк. Ранее выполненные импорты не восстанавливаются задним числом.

JSON сохраняется как данные, включая неизвестные поля, null, пустые объекты и
массивы; пробелы и порядок ключей исходного текста не сохраняются. result_payload
является снимком результата на момент обработки и не меняется при следующем импорте.
Отдельный экран просмотра истории и повторной обработки конкретного отказа пока
не добавлен. Журнал можно просматривать SQL-запросами из DATABASE.md.

## Очистка данных для ручного тестирования

В Angular добавлена кнопка «Очистить тестовую базу» с подтверждением.
Она вызывает `POST /api/shops/1/test-data/reset` с JSON `{"confirm":true}`.
Ответ: `{"shop_id":1,"status":"cleared"}`. Это функция локального тестового
окружения: в production запрос возвращает 404. Для нового теста миграции
повторно применять не нужно. Счётчики AUTO_INCREMENT не сбрасываются.

В одной транзакции удаляются запуски импорта и заказы указанного магазина;
внешние ключи удаляют связанные позиции, строки журнала и отказы. Магазин,
тарифы, данные других магазинов и история миграций сохраняются. Очистка не
создаёт запись журнала импорта, поскольку удаляет сам журнал.

Требуются Content-Type application/json и явное confirm=true, иначе 415/400.
Неизвестный магазин — 404; незавершённый запуск со status=processing — 409;
ошибка базы — 503. Блокировка строки магазина не позволяет новой пачке
начаться во время очистки. Импорт и очистка взаимно блокируются кнопками
на странице. После успеха старый отчёт очищается и показывается сообщение;
при сетевой ошибке состояние удаления неизвестно, очистку можно повторить.
