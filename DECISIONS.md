# Журнал решений

## Этап 1 — окружение и каркас

### Запуск

Требуются Docker Engine / Docker Desktop и Docker Compose v2. Локальные PHP, Composer,
Node.js и MySQL не нужны. Первый запуск требует доступа к реестрам образов и пакетов.
Все команды выполняются из корня репозитория:

```sh
cp docker/.env.example docker/.env
docker compose -f docker/compose.yaml up -d --build --wait
docker compose -f docker/compose.yaml exec backend php bin/console doctrine:migrations:migrate --no-interaction
```

Открыть http://localhost:8080. Страница проверяет API и подключение к базе.
Проверка API: `curl -fsS http://localhost:8080/api/health`.
Ожидаемый ответ: `{"status":"ok","database":"ok"}`.

```sh
# Состояние и логи
docker compose -f docker/compose.yaml ps
docker compose -f docker/compose.yaml logs --tail=100
# Сборка Angular
docker compose -f docker/compose.yaml exec frontend npm run build
# Проверка контейнера Symfony
docker compose -f docker/compose.yaml exec backend php bin/console lint:container
# Остановка с сохранением данных
docker compose -f docker/compose.yaml down
```

Порт приложения можно изменить через `APP_PORT` в `docker/.env`, MySQL — через
`MYSQL_PORT` (по умолчанию `3307`). Данные MySQL сохраняются в
именованном томе. Не добавляйте `-v` к `down`, если данные нужны.
Пароли из примера предназначены только для локальной разработки. При смене паролей
после первого запуска существующая база автоматически их не обновляет.

### Архитектура

- `backend/` — монолит Symfony: одно приложение, единая точка входа и база.
- `frontend/` — Angular, standalone-компонент и signals для состояния страницы.
- `docker/` — вся Docker-инфраструктура: Compose, Dockerfile, конфигурация Nginx,
  примеры переменных окружения и исключения контекста сборки.
- Четыре контейнера: Nginx, PHP-FPM, Angular dev server и MySQL 8.0.
  MySQL выбрана по обязательному условию задания; PostgreSQL не используется.
- Nginx публикует только один локальный порт. `/api/` идёт в Symfony, остальные
  запросы — в Angular. Общий origin избавляет от необходимости настраивать CORS.
- PHP 8.3 и Symfony 7.4 LTS. Composer подбирает зависимости с учётом PHP 8.3;
  версии пакетов сохранены в `composer.lock`.
- Angular 21 и Node 22 совместимы; версии пакетов сохранены в `package-lock.json`.
  Основание: https://angular.dev/reference/versions и https://symfony.com/releases/7.4.
- Образы закреплены по веткам, не по digest: обновления образов возможны при повторной
  загрузке. Для тестового окружения это допустимо; полностью воспроизводимые образы
  потребуют фиксации digest.
- Исходники подключены в контейнеры для разработки. После изменения зависимостей
  нужна повторная сборка. База теперь доступна на `127.0.0.1:3307`.
- `/api/health` выполняет `SELECT 1`. При недоступности базы возвращает
  HTTP 503 без внутренних подробностей. На этапе создания базы соединение переведено
  на Doctrine DBAL, общий для API и миграций.

### Границы этапа

На этапе окружения импорт, тарифы, таблицы заказов и фильтрация ещё не были реализованы.
Результат следующего этапа описан ниже. Тесты бизнес-логики появятся вместе с ней.
Авторизация, CI, очереди, деплой и production-сборка окружения не входят в этот этап.
На странице пока только проверка подключения, а не интерфейс импорта.

Исходное задание сохранено в README.MD без изменения текста. В приложенном JSON
есть переносы внутри ключей и значений: перед созданием фикстуры их нужно убрать,
сохранив намеренно некорректные бизнес-данные.

## Структура базы — 10 октября 2026

Подробная схема, доступы и команды находятся в [DATABASE.md](DATABASE.md).

### Решения

- Созданы четыре прикладные таблицы: `shops`, `delivery_tariffs`, `orders`, `order_items`.
  Историю миграций ведёт `doctrine_migration_versions`.
- Для доступа к базе выбран Doctrine DBAL и Doctrine Migrations. Рассматривали ORM:
  для небольшого импорта с явными запросами и блокировками DBAL достаточно; ORM можно
  добавить позже, если это упростит развитие модели.
- Позиции храним отдельными строками, чтобы обеспечить внешние ключи, ограничения
  количества/цены и доступ к отдельным позициям. Покупатель хранится в заказе как снимок,
  отдельный справочник клиентов пока не нужен.
- Деньги — `BIGINT` в копейках. Позиции, доставка и итог используют целочисленную
  арифметику. База вычисляет производные суммы и `needs_review`, чтобы они не расходились
  с исходными полями. Сумму всех позиций заказа проверит приложение в транзакции.
- Стоимость доставки сохраняется при импорте. Она не пересчитывается при чтении
  и не меняется вслед за правками тарифов.
- Время — UTC в `DATETIME(6)`, зона магазина и её снимок в заказе — IANA-строка.
  MySQL запускается с `--default-time-zone=+00:00`. Преобразование входных дат в UTC
  будет обязанностью сервиса импорта.
- Ограничение `UNIQUE(shop_id, marketplace_id)` — основа защиты от дублей.
  Для корректного обновления статуса при конкуренции позже добавим транзакции,
  блокировку строки и обработку конфликта уникальности. Одна схема не задаёт ответ API.
- Индексы списка: `(shop_id, id)` и `(shop_id, status, id)`; планируем сортировку
  и пагинацию по внутреннему ID. Поиск по покупателю или адресу пока не требуется.
- Две миграции разделяют структуру и начальные данные. DDL-миграция нетранзакционная:
  MySQL выполняет неявные commit при DDL; сидирование — в отдельной транзакционной
  миграции. Основание: [Doctrine Migrations](https://www.doctrine-project.org/projects/doctrine-migrations/en/3.9/explanation/implicit-commits.html).
  При частичном сбое DDL потребуется проверить созданные таблицы перед повторным запуском.
- Проверки допустимых значений дублируются на уровне базы через `CHECK` и внешние ключи;
  API всё равно должен валидировать данные и давать понятную причину отказа.
  Ограничения MySQL: [официальная документация](https://dev.mysql.com/doc/refman/8.0/en/create-table-check-constraints.html).
- MySQL опубликована на `127.0.0.1:3307` по запросу пользователя для локального клиента.
  Внутренний адрес бэкенда — `database:3306`. Параметры можно изменить через `docker/.env`.
- Генерируемый Symfony файл `config/reference.php` исключён из Git; он обновляется
  самим фреймворком при изменении конфигурации бандлов.

### Допущения и ограничения

- ID площадки чувствителен к регистру, максимум 128 символов; коды района — до 64.
  Ввод длиннее этих границ будущий валидатор отклоняет, не обрезает.
- Количество — положительное целое; цена может быть нулевой. Дробные количества
  в задании отсутствуют. Импорт также должен ограничить деньги и произведения
  диапазоном 64-битного целого без переполнения.
- Начало интервала должно быть раньше конца. Московскую дату и время объединяем
  в полный момент времени перед переводом в UTC. Прошедшая дата доставки сама по себе
  допустима: фикстура содержит исторические завершённые заказы.
- Для самовывоза доставка стоит 0; адрес, район и интервал в базе пусты.
- Отсутствие тарифа будет проверять импорт. Сохранённый заказ не связан внешним ключом
  с текущим тарифом: справочник может меняться, а снимок заказа должен сохраняться.
- Проверки «хотя бы одна позиция» и запрет изменения финального статуса требуют
  бизнес-логики следующего этапа. Триггеры и таблицы аудита импортов пока не добавлены.
- Для тестового магазина `id = 1`, `code = demo`. Начальные данные версионируются
  миграцией; повторный запуск не сбрасывает вручную изменённые тарифы.

## Импорт заказов — 12 октября 2026

Согласованная схема реализована в бэкенде. Контракт и подробные правила —
в [IMPORT.md](IMPORT.md). Фронтенд получает по одной строке результата на каждую
входную запись с исходным индексом, результатом, кодом и текстом причины, предупреждениями
и сохранёнными суммами. Кнопка и отображение этого ответа остаются следующим этапом UI.

### Решения и допущения

- Валидация, расчёт доставки, транзакционное сохранение и HTTP-контроллер разделены.
  Валидатор возвращает нормализованные данные; для ожидаемых отказов есть `OrderRejected`.
- ID внутри пачки запоминается перед проверкой остальных полей. Даже если первое
  вхождение отклонено, второе остаётся дублем — первое вхождение обрабатывается обычно.
- При повторном импорте проверяем весь входной заказ. Если он валиден, меняется только
  статус; остальные поля и позиции остаются первоначальными. Ответ показывает сохранённые
  суммы. Это означает, что повреждённый повторный заказ будет отклонён, а не применён
  частично как обновление статуса.
- Финальные статусы `delivered` и `cancelled` неизменны. Для нефинальных статусов
  дополнительные ограничения порядка не вводились: задание их не задаёт.
- Бесплатный порог включителен. Срочность — менее 7200 секунд от создания до начала
  доставки. Ровно два часа без надбавки; доставка раньше создания отклоняется.
  Самовывоз всегда бесплатен. Прошедшие даты допустимы, поскольку импортируются
  исторические заказы. Интервал через полночь пока не поддерживается.
- Деньги переводятся в копейки разбором десятичного представления, без арифметики
  с float. Лимит итоговой суммы — 1000000000000 копеек, чтобы ограничить значения
  и избежать переполнения. Обязательны `total`, `created_at`, имя/цена/количество позиции;
  SKU необязателен. Ограничения размеров и остальные допущения описаны в IMPORT.md.
- На один заказ одна транзакция, включающая все позиции. Вставки защищены уникальным
  индексом. Для существующего заказа финальный статус проверяется после блокировки
  строки, по её последнему состоянию. Первичный поиск не блокирует отсутствующую строку,
  чтобы не создавать лишних gap-lock при конкурентных вставках.
- Конфликт уникальности и ошибки блокировок повторяют транзакцию до трёх попыток.
  При исчерпании или другой ошибке базы текущая запись возвращает `storage_error`,
  транзакция откатывается, остальные записи продолжают обрабатываться.
  Основание: [Doctrine DBAL — транзакции](https://www.doctrine-project.org/projects/doctrine-dbal/en/3.8/reference/transactions.html).
- Успешно разобранная пачка отвечает HTTP 200, даже если есть отказы. Ошибки самого
  запроса имеют отдельные HTTP-коды и JSON-формат. Постоянный журнал импортов не добавлялся.

### Что требуется в реальном обмене

Обновления заказов могут поступать не в порядке дат и статусов. `created_at` не отражает
свежесть статуса, а наш `orders.updated_at` — время локальной обработки. Для реального
обмена требуются `updated_at` источника либо монотонная версия заказа и атомарное
сравнение с сохранённой версией. Для одинаковых времён нужен дополнительный порядок.
Без этих данных нельзя отличить актуальный нефинальный статус от запоздавшего события.
В текущем задании соблюдаем согласованное правило: очередной статус применяется,
финальные статусы сохраняются. Поле версии не добавлено: источник его не передаёт.

### Проверка и AI

Пройдены проверки валидации и доставки, реальные транзакции на MySQL, повторный импорт,
два параллельных импорта и конкурирующие обновления статуса. Отдельно проверен откат
заказа при сбое записи позиции. HTTP-контракт проверен через Symfony Kernel.
Всего 60 тестов и 150 проверок, включая ранее созданные проверки схемы.
AI использован для реализации и тестов; ожидаемые суммы сверены с исходными тарифами
и фактическими результатами MySQL. Фикстура для тестов берётся из того же файла,
который будет отправлять фронтенд, через read-only Docker-монтирование.

## Последний результат импорта в orders — 12 октября 2026

По запросу пользователя добавлено `orders.outcome` новой миграцией. Допустимы
`created`, `updated`, `unchanged`; существующие записи остаются с `NULL` до
следующей успешной обработки, чтобы не выдумывать историю. Изменение поля
происходит внутри транзакции заказа и не меняет смысл бизнес-статуса. Дубль
внутри пачки не затирает результат первого вхождения. Отказы остаются в API,
поскольку неполные записи не соответствуют ограничениям таблицы orders.
Поле хранит последнее значение, полноценный журнал пока не реализован.

В интеграционных тестах проверены сохранённые исходы первого и повторного
импорта, смены статуса и сохранения финального статуса.

## Постоянный журнал импорта и отказы — 12 октября 2026

Добавлены order_imports (запуски), order_import_records (каждая запись) и
rejected_orders (отказы). Журнал сохраняет исходные данные и снимок ответа,
в том числе по повторным попыткам; API возвращает import_id. Рабочие заказы
и их outcome остаются отдельно. Принятый заказ и запись журнала атомарны;
отказ и его запись журнала также атомарны. Недоступность журнала не маскируется
успешным ответом. История сохраняется при удалении рабочего заказа.

Исходный JSON HTTP-запроса передаётся в журнал до преобразования объектов в
ассоциативные массивы, поэтому различие {} и [] сохраняется. Старые попытки
не восстанавливаются. Просмотр истории пока через SQL; экран истории и
автоматический повтор конкретного отказа не входят в этот этап.

Тесты проверяют первый и повторный импорт, конкуренцию, сохранение исходных
отказов, некорректные записи, пустые пачки, откат при недоступном журнале
и сохранение истории после исправления и удаления заказа.

## Кнопка очистки тестовых данных — 12 октября 2026

Добавлено подтверждение очистки и POST /api/shops/{shopId}/test-data/reset.
Очистка доступна только в dev/test и только с JSON confirm=true. Удаляются
заказы и история выбранного магазина; магазин, тарифы и другие магазины
сохраняются. Строка магазина блокируется на время транзакции, незавершённый
импорт запрещает очистку. Счётчики ID не сбрасываются.

В Angular предусмотрены отмена, блокировка кнопок, сообщение результата
и ошибок, очистка старого отчёта. Проверены сборка Angular, подтверждение
и отмена в браузере; интеграционные тесты проверяют удаление на отдельных
магазинах, повторный импорт после очистки, изоляцию других магазинов,
невалидные запросы, незавершённый импорт и запрет production.

## Фильтр отчёта на мобильном экране — 12 октября 2026

На ширине до 640 px системный select заменён группой кнопок для каждого
результата. Размеры нативного всплывающего меню на настольной ОС не контролируются
CSS страницы, что давало мелкие опции в режиме просмотра 425 px. Мобильные
кнопки имеют текст 16 px, высоту не менее 48 px и aria-pressed для текущего
выбора. На широком экране сохранён select; оба элемента используют один filter.

## Счётчики как фильтр отчёта — 12 октября 2026

По предложению пользователя summary-item стали кнопками фильтра на всех
экранах. Удалены select и отдельные мобильные опции. Выбранный счётчик
выделяется цветом и aria-pressed; повторное нажатие снимает фильтр.
Также доступна кнопка «Показать все». Сами счётчики всегда относятся
ко всей пачке, подпись показывает количество видимых строк из общего числа.
