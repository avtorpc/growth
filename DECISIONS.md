# Журнал решений

## Этап 1 — окружение и каркас

### Запуск

Требуются Docker Engine / Docker Desktop и Docker Compose v2. Локальные PHP, Composer,
Node.js и MySQL не нужны. Первый запуск требует доступа к реестрам образов и пакетов.
Все команды выполняются из корня репозитория:

```sh
cp docker/.env.example docker/.env
docker compose -f docker/compose.yaml up -d --build --wait
docker compose -f docker/compose.yaml exec backend php bin/console doctrine:migrations:migrate --no-interaction
```

Открыть http://localhost:8080. Страница проверяет API и подключение к базе.
Проверка API: `curl -fsS http://localhost:8080/api/health`.
Ожидаемый ответ: `{"status":"ok","database":"ok"}`.

```sh
# Состояние и логи
docker compose -f docker/compose.yaml ps
docker compose -f docker/compose.yaml logs --tail=100
# Сборка Angular
docker compose -f docker/compose.yaml exec frontend npm run build
# Проверка контейнера Symfony
docker compose -f docker/compose.yaml exec backend php bin/console lint:container
# Остановка с сохранением данных
docker compose -f docker/compose.yaml down
```

Порт приложения можно изменить через `APP_PORT` в `docker/.env`, MySQL — через
`MYSQL_PORT` (по умолчанию `3307`). Данные MySQL сохраняются в
именованном томе. Не добавляйте `-v` к `down`, если данные нужны.
Пароли из примера предназначены только для локальной разработки. При смене паролей
после первого запуска существующая база автоматически их не обновляет.

### Архитектура

- `backend/` — монолит Symfony: одно приложение, единая точка входа и база.
- `frontend/` — Angular, standalone-компонент и signals для состояния страницы.
- `docker/` — вся Docker-инфраструктура: Compose, Dockerfile, конфигурация Nginx,
  примеры переменных окружения и исключения контекста сборки.
- Четыре контейнера: Nginx, PHP-FPM, Angular dev server и MySQL 8.0.
  MySQL выбрана по обязательному условию задания; PostgreSQL не используется.
- Nginx публикует только один локальный порт. `/api/` идёт в Symfony, остальные
  запросы — в Angular. Общий origin избавляет от необходимости настраивать CORS.
- PHP 8.3 и Symfony 7.4 LTS. Composer подбирает зависимости с учётом PHP 8.3;
  версии пакетов сохранены в `composer.lock`.
- Angular 21 и Node 22 совместимы; версии пакетов сохранены в `package-lock.json`.
  Основание: https://angular.dev/reference/versions и https://symfony.com/releases/7.4.
- Образы закреплены по веткам, не по digest: обновления образов возможны при повторной
  загрузке. Для тестового окружения это допустимо; полностью воспроизводимые образы
  потребуют фиксации digest.
- Исходники подключены в контейнеры для разработки. После изменения зависимостей
  нужна повторная сборка. База теперь доступна на `127.0.0.1:3307`.
- `/api/health` выполняет `SELECT 1`. При недоступности базы возвращает
  HTTP 503 без внутренних подробностей. На этапе создания базы соединение переведено
  на Doctrine DBAL, общий для API и миграций.

### Границы этапа

На этапе окружения импорт, тарифы, таблицы заказов и фильтрация ещё не были реализованы.
Результат следующего этапа описан ниже. Тесты бизнес-логики появятся вместе с ней.
Авторизация, CI, очереди, деплой и production-сборка окружения не входят в этот этап.
На странице пока только проверка подключения, а не интерфейс импорта.

Исходное задание сохранено в README.MD без изменения текста. В приложенном JSON
есть переносы внутри ключей и значений: перед созданием фикстуры их нужно убрать,
сохранив намеренно некорректные бизнес-данные.

### AI и время

AI использован для создания каркаса, конфигураций и проверки запуска. Во время
проверки исправлен подбор транзитивных Symfony-пакетов: без `config.platform.php`
Composer выбирал зависимости для более новой PHP, чем в контейнере приложения.
Время и фактические результаты проверок записаны ниже по окончании этапа.

### Результаты проверки (10 октября 2026)

- Первичная сборка образов и запуск на новом томе MySQL выполнены успешно.
- Angular `npm run build` — успешно.
- Symfony `lint:container` и Composer `validate --strict` — успешно.
- `GET /api/health` через Nginx — HTTP 200, база доступна.
- Страница открыта в браузере: Angular показывает успешное подключение.

## Структура базы — 10 октября 2026

Подробная схема, доступы и команды находятся в [DATABASE.md](DATABASE.md).

### Решения

- Созданы четыре прикладные таблицы: `shops`, `delivery_tariffs`, `orders`, `order_items`.
  Историю миграций ведёт `doctrine_migration_versions`.
- Для доступа к базе выбран Doctrine DBAL и Doctrine Migrations. Рассматривали ORM:
  для небольшого импорта с явными запросами и блокировками DBAL достаточно; ORM можно
  добавить позже, если это упростит развитие модели.
- Позиции храним отдельными строками, чтобы обеспечить внешние ключи, ограничения
  количества/цены и доступ к отдельным позициям. Покупатель хранится в заказе как снимок,
  отдельный справочник клиентов пока не нужен.
- Деньги — `BIGINT` в копейках. Позиции, доставка и итог используют целочисленную
  арифметику. База вычисляет производные суммы и `needs_review`, чтобы они не расходились
  с исходными полями. Сумму всех позиций заказа проверит приложение в транзакции.
- Стоимость доставки сохраняется при импорте. Она не пересчитывается при чтении
  и не меняется вслед за правками тарифов.
- Время — UTC в `DATETIME(6)`, зона магазина и её снимок в заказе — IANA-строка.
  MySQL запускается с `--default-time-zone=+00:00`. Преобразование входных дат в UTC
  будет обязанностью сервиса импорта.
- Ограничение `UNIQUE(shop_id, marketplace_id)` — основа защиты от дублей.
  Для корректного обновления статуса при конкуренции позже добавим транзакции,
  блокировку строки и обработку конфликта уникальности. Одна схема не задаёт ответ API.
- Индексы списка: `(shop_id, id)` и `(shop_id, status, id)`; планируем сортировку
  и пагинацию по внутреннему ID. Поиск по покупателю или адресу пока не требуется.
- Две миграции разделяют структуру и начальные данные. DDL-миграция нетранзакционная:
  MySQL выполняет неявные commit при DDL; сидирование — в отдельной транзакционной
  миграции. Основание: [Doctrine Migrations](https://www.doctrine-project.org/projects/doctrine-migrations/en/3.9/explanation/implicit-commits.html).
  При частичном сбое DDL потребуется проверить созданные таблицы перед повторным запуском.
- Проверки допустимых значений дублируются на уровне базы через `CHECK` и внешние ключи;
  API всё равно должен валидировать данные и давать понятную причину отказа.
  Ограничения MySQL: [официальная документация](https://dev.mysql.com/doc/refman/8.0/en/create-table-check-constraints.html).
- MySQL опубликована на `127.0.0.1:3307` по запросу пользователя для локального клиента.
  Внутренний адрес бэкенда — `database:3306`. Параметры можно изменить через `docker/.env`.
- Генерируемый Symfony файл `config/reference.php` исключён из Git; он обновляется
  самим фреймворком при изменении конфигурации бандлов.

### Допущения и ограничения

- ID площадки чувствителен к регистру, максимум 128 символов; коды района — до 64.
  Ввод длиннее этих границ будущий валидатор отклоняет, не обрезает.
- Количество — положительное целое; цена может быть нулевой. Дробные количества
  в задании отсутствуют. Импорт также должен ограничить деньги и произведения
  диапазоном 64-битного целого без переполнения.
- Начало интервала должно быть раньше конца. Московскую дату и время объединяем
  в полный момент времени перед переводом в UTC. Прошедшая дата доставки сама по себе
  допустима: фикстура содержит исторические завершённые заказы.
- Для самовывоза доставка стоит 0; адрес, район и интервал в базе пусты.
- Отсутствие тарифа будет проверять импорт. Сохранённый заказ не связан внешним ключом
  с текущим тарифом: справочник может меняться, а снимок заказа должен сохраняться.
- Проверки «хотя бы одна позиция» и запрет изменения финального статуса требуют
  бизнес-логики следующего этапа. Триггеры и таблицы аудита импортов пока не добавлены.
- Для тестового магазина `id = 1`, `code = demo`. Начальные данные версионируются
  миграцией; повторный запуск не сбрасывает вручную изменённые тарифы.
